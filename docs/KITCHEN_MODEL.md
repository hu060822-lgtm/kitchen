# 料理模型（CookingSystem）

程式：`shared/src/kitchen/model.ts`（熱與狀態）、`taste.ts`（口味）、`data.ts`（食材、食譜、需求）、`server/src/kitchen/sim.ts`（工作站）、`scoring.ts`（評分）。
全部是純函式加上固定步長（`DT` = 0.1 秒）的模擬：同樣的初始狀態、同樣的操作序列，結果逐位元相同（`驗收 1`）。

## 1. 鍋子與火力

| 火力 | 爐火目標溫度 |
| --- | --- |
| 關火 | 22°C（室溫） |
| 小火 | 130°C |
| 中火 | 180°C |
| 大火 | 240°C |

鍋溫每一步以 `1 − e^(−k·dt)` 的比例靠近目標：平底鍋 k = 0.35、湯鍋 k = 0.12。湯鍋裡有液體時鍋溫上限 100°C。倒入冷的高湯會依份量拉低鍋溫。

這就是熱慣性：轉小火後鍋子要一陣子才降溫，關火後的餘溫還會煮東西。

## 2. 食材受熱

食材感受到的溫度：`effective = v ≤ 100 ? v : 100 + (v − 100) × 0.25`（表面很燙，但中心不會超過太多）。

- 中心溫度以 `k × 切法係數` 靠近 effective（烤麵包機固定 120°C）。
- 熟度：中心溫度超過「開始變熟」後，每秒 +（溫度 − 起點）/ 300。
- 上色：鍋溫超過 150°C 時，每秒 +（鍋溫 − 150）/ 600 × 食材的上色倍率。平底鍋只上色朝下的一面（翻面交換兩面）；湯鍋乾炒時有攪拌（6 秒內）兩面各 55%，太久沒攪拌貼鍋的一面 130%；湯裡不上色。烤麵包機每秒 +段數 × 0.03 × 倍率，兩面一起。
- 任一面上色 ≥ 2.0 → 燒焦；熟度 ≥ 燒焦值 → 燒焦。
- 離開熱源：中心溫度以 0.012／秒 回到室溫；中心還熱的時候熟度繼續增加（餘熱）。
- 湯鍋乾炒、鍋溫 > 150°C、超過 6 秒沒攪拌：焦底值累積，盛起來時整碗帶苦味。

切法係數（受熱速度）：整塊 0.55、切片 1、切丁 1.15、切碎 1.25、剁末 1.45、打散 1.3。

## 3. 狀態機

合法的轉換（伺服器拒絕其他所有轉換）：

- 清洗：在水槽，2 秒；煮過的不能洗。
- 去皮：在備料台，2.5 秒；需要去皮的食材沒削皮不能切。
- 切：在備料台，選切法後照節奏下刀；每份只能切一次；切法必須是這種食材允許的。
- 汙染：在砧板上切生肉 → 砧板被汙染；之後在同一塊砧板切的非肉類食材被標記汙染，擦砧板（2 秒）解除。
- 加熱：平底鍋、湯鍋、烤麵包機；烹調方式會被記錄（評分用）。
- 調味：量匙量好後倒進鍋裡（平均分給鍋中每份食材）或盤子上。
- 裝盤：放到裝盤區的盤子；湯鍋的內容用碗「盛起來」（連同鍋中調味一起）。

衍生狀態（用於描述與評分）：`cookingState`（生、加熱中、熟、過熟、燒焦）、`flavorBand`（生、熟、上色、燒焦）、`freshnessState`。

一致性 = `1 − 變異係數 × 2.2 − 太急的比例 × 0.6`（間隔 < 110 ms 算太急），範圍 0–1。只看玩家實際的下刀時間；同樣的節奏永遠同樣的分數。

## 5. 口味

整道菜的口味 = Σ（每份食材在目前口味階段的味道 × 數量）＋ 焦底的苦味 ＋ 調味料，再 ÷ max(1, 總份量)。七個維度：鹹、甜、酸、鮮、辛辣、苦、香濃。每份食材依熟度與上色落在「生／熟／上色／燒焦」其中一個口味階段（完整表格在遊戲內 R 鍵）。

| 調味料（每 1 匙） | 味道 |
| --- | --- |
| 鹽 | 鹹 2 |
| 糖 | 甜 2 |
| 醬油 | 鹹 1.2、鮮 0.8 |
| 醋 | 酸 2 |
| 黑胡椒 | 辛辣 0.8、香濃 0.2 |
| 油 | 香濃 0.8 |

試吃的描述：< 0.4 幾乎沒有、< 1.0 淡淡的、< 1.8 明顯、< 2.6 很重、≥ 2.6 太重了。

## 6. 評分

見 [`GAME_DESIGN.md`](GAME_DESIGN.md) 3.1。補充：

- 熟度／上色在區間外時依距離線性遞減（熟度的容忍寬度至少 0.6，上色 0.6）。
- 招牌菜的調味：每種配方調味料 `1 − |實際 − 配方| ÷ max(配方, 0.5)`；配方外的調味料 ≥ 0.5 匙扣 0.25。
- 自選的口味：在區間內 1；每偏離 1 扣 0.5。沒指定苦味時，苦味 > 1 也會扣分。
- 多放的成分：製程分 × (1 − 0.12 × 多放的數量)。
- 效率：≤ 標準 × 0.8 快、≤ 標準 × 1.3 準時、其他慢。

## 拿取與暫放（試玩回饋）

- 物品欄：**左手、右手、菜籃 2 格**（`PlayerKitchen.held`＝目前用的手、`other`＝另一隻手、`side`＝目前是哪隻手、`basket`＝菜籃）。菜籃只放還沒處理過的原料。單手廚師只有一隻手。
- 拿新東西：目前的手空著就用它，不然改用空著的另一隻手（`freeHand`）；兩隻手都滿才拿不下。貨箱、一疊髒盤要用雙手（兩隻手都要空著，拿著時不能換手、不能再拿別的）。
- 目前的手用掉（放下、下鍋、交給隊友、掉在地上）之後：菜籃有原料就補到手上；菜籃空了、另一隻手有東西，就改用另一隻手。
- 動作要用的東西在另一隻手時自動換手（`HAND_NEED`：放上砧板用食材、加調味用量匙、出餐用盤子…）。也可以自己換手（`stationId: 'self'`、`action: 'swap'`；客戶端 B 鍵或滑鼠滾輪）。
- 冷藏架／乾貨架的 `take` 帶 `count`（1–4）：依序放進目前的手、另一隻手、菜籃；放不下時拿得到多少算多少，訊息會說放在哪裡。`store_all` 把兩隻手與菜籃裡屬於這個架子的原料全部放回。
- 交接、接住快掉的東西、撿地上的東西都用同一套規則（一隻手空著就接得下；要用雙手的東西要兩隻手都空著）。奶油手的失衡跟著東西走：換手不算放下。
- 客戶端快捷鍵：注視冷藏架／乾貨架按數字鍵 1–9 直接拿第幾種（不必打開面板），Shift＋數字拿到滿；面板裡數字鍵依「一次拿 ×N」的設定拿。
- 成品架（`rack_meat`、`rack_veg`，中島旁）：各放 `RACK_CAPACITY`＝6 份。肉類（`meat: true`）只能放肉類架，其他只能放另一個架（生肉不碰到要生吃的菜）。`place`、`place_all`（手上＋菜籃裡適合的全部放上去，其他留在手上）、`pick`。

### 要在水裡煮的食材

白米、義大利麵、蛤蜊、米粉（`needsLiquid`）：不在湯鍋的湯裡時，熟化速度只有 15%（`DRY_COOK_FACTOR`）——乾鍋炒生米不會變成飯。泡軟的米粉例外（70%），所以米粉要先泡再炒。

水：水槽「接一杯水」（或乾貨架拿），倒進湯鍋增加湯量；沒有味道，會把湯沖淡（口味除以份量）。

### 水槽：浸泡

水槽可以放兩樣東西。可浸泡的食材（米粉）放進去後按「放水泡」：每秒 +1／20，1＝泡軟，超過 2.5＝泡爛（第二階段會影響質地）。拿走最後一樣可浸泡的東西時自動放掉水。

### 烤箱（新工作站，廚房東牆、監視器與置物櫃之間）

| 設定 | 目標溫度 |
| --- | --- |
| 低 | 170°C |
| 中 | 210°C |
| 高 | 250°C |

- 預熱：每秒以 `1 − e^(−0.06·dt)` 靠近目標（比湯鍋還慢，中溫大約 75 秒），預熱好會通知所有人。
- 熱空氣：中心溫度靠近的速度是鍋子的 0.55 倍。
- 上色：兩面同時，每面的速度是平底鍋朝下那面的 0.18 倍——不用翻面、比較均勻、比較慢，適合放著去做別的事。
- 最多四份；液體不能直接放。怕火廚師要戴手套、最多中溫（和其他火源一樣）。
- 烹調方式記為 `oven`。

### 攪拌碗（新工作站，中島北側、調味區旁）

把 2–6 樣東西放進碗裡按「攪拌」（2.5 秒），合成一份：

| 種類 | 條件 | 例子 |
| --- | --- | --- |
| 麵糊 batter | 麵粉＋液體或蛋液，其他固體都是小塊 | 麵粉＋牛奶＋蛋液 |
| 餡料 bound | 絞肉／剁末／壓碎的食材＋蛋液或麵粉 | 豬絞肉＋洋蔥末＋蛋液、鷹嘴豆泥＋麵粉 |
| 拌料 tossed | 其他 | 高麗菜絲＋胡蘿蔔絲＋檸檬汁 |

- 主體決定加熱曲線：還沒熟的肉類／海鮮優先（要熟透才安全），麵糊是麵粉，其他是最難熟的固體；液體永遠不是主體。
- 拌好的一份比較厚，受熱 0.75 倍。不能再洗、切或放回架上。
- 裝盤時展開成每一種食材各一個成分（`mixedWith` 記得原本屬於哪一份）：拌進去的食材跟著主體受熱——溫度、上色增量、加熱方式相同，熟度依主體「拌好後多熟了幾成」換算到自己的曲線。現有的評分不用改就能處理；第二階段的自由料理判定會用 `mixedWith` 認出麵糊與餡料。

## 料理沙盒擴充 v3.0：第二階段（自由料理核心）

程式：`shared/src/kitchen/dish.ts`（純函式，伺服器出餐時呼叫；客戶端只顯示結果）。不選食譜、直接拿食材做菜，系統只看盤子（碗）裡實際的東西，判定這道菜是什麼。同樣的內容永遠得到同樣的名稱、分類、品質與原因。

### 料理容器紀錄

每個成分帶著完整狀態：份量、處理（洗、削、切法）、加入的時間與地點（最後一次放上熱源或攪拌碗）、各種熱源上的受熱秒數（`cookSec`：煎、乾炒、湯裡、烤箱、烤麵包機）、最後一次受熱的方式（`lastMode`）、碰過的最高鍋溫（`peakHeat`）、翻面次數、熟度、上色、拌料群組（`mixedWith`）。盤子另外記錄調味與湯鍋盛起來時剩下的湯量（`liquid`）。出餐結果的 `analysis.record` 就是這份紀錄，`analysis.order` 是下鍋順序。

### 烹調方式與成品形式

- 烹調方式：依每個固體成分「最後一次受熱的方式」投票（份量加權）。平底鍋上小塊、打散、切絲的為主＝炒，整塊片狀為主＝煎；湯鍋乾炒＝炒；湯裡平均超過 90 秒＝燉，否則＝煮；烤箱＝烤；完全沒受熱＝生食／拌。所以「先煮熟的飯再下鍋炒」是炒飯。
- 成品形式：麵糊煎成的＝煎餅；餡料＝餅／肉餅；吐司；有麵條＝麵；有米＝飯（燉煮成湯＝粥）；生的＝沙拉；烤箱＝烤盤；有湯＝湯；其他＝一盤菜。
- 湯裡不會燒焦：泡在湯裡的食材熟度最多到燒焦值的 90%（只會煮爛）。燉菜裡煮過「剛好熟」的蔬菜與肉不扣分（燉得軟爛入味）；麵和飯例外，還是會糊。

### 醬汁狀態

液體量＝湯鍋盛起來剩下的湯（或液體成分）＋檸檬汁＋含水量高的蔬菜煮過頭出的水。增稠＝在湯裡煮過的增稠食材（麵粉、馬鈴薯、玉米、鷹嘴豆、鮮奶油）、融化的起司、壓碎的食材。

| 狀態 | 條件 |
| --- | --- |
| 乾的 | 液體 < 0.15 杯 |
| 濃稠 | 增稠／液體 ≥ 0.9 |
| 奶醬／醬汁 | ≥ 0.35（有乳製品＝奶醬） |
| 湯 | 液體 ≥ 1.2 杯而且是碗、煮或燉 |
| 出水 | 盤子上的液體 ≥ 0.6 杯 |

### 分類與名稱

1. **已知食譜**：食譜的每個必要成分都有、烹調方式對、多出來的食材不超過一種 → 用食譜名稱。
2. **變體**：用了食譜允許的替代食材（`RecipeComponent.alt`）、烹調方式不同、或多加了 2–3 種食材，但至少一半的必要成分還是原本的食材 → 名稱裡的食材換成實際用的（黑胡椒牛肉 → 黑胡椒豬肉），否則加上「（X 版）」。
3. **新創**：都不符合 → 名稱由實際內容組成：風味特徵（檸檬、辣味、薑香、蒜香、黑胡椒、醬燒、蔥香；起司、奶油）＋主要食材（蛋白質優先、再來是蔬菜，依份量）＋形式（炒、香煎、水煮、燉、湯、煲、濃湯、炒飯、燴飯、粥、炒麵、湯麵、煎餅、肉餅、沙拉、涼拌、烤盤、焗烤）。風味詞要真的吃得出來才會出現（放了一點辣椒但不辣，就不會叫「辣味」）。
4. **失敗**：有致命失誤或品質低於 40 → 名稱前面加上原因：燒焦的、過鹹的、苦掉的、糊掉的、沒煮熟的。致命失誤：主要食材或主食燒焦、肉沒熟（食品安全）、生米乾麵沒在水裡煮、麵粉沒煮熟、鹹度 > 3.2、苦度 > 2、麵飯嚴重糊掉、沒有固體食材。

### 一些做法的規則

- 湯鍋可以「撈起來」：煮好的義大利麵、白飯、燙過的花椰菜撈出來，再拿去炒、拌醬汁或進烤箱（湯留在鍋裡）。
- 海鮮炒飯要先把米加水煮熟、撈起來再炒；直接炒生米會判定成「沒煮熟的蛋炒飯」。
- 米粉要先在水槽泡軟再炒。
- 蔬菜煎餅：麵粉、蛋液、水、切碎的蔬菜在攪拌碗拌成麵糊再煎。玉米起司煎蛋：蛋液、玉米、起司拌好再煎。起司焗花椰菜：燙過的花椰菜、麵粉、牛奶、起司拌好進烤箱。
- 培根高麗菜、蛤蜊蔬菜湯不另外調味：食材本身就鹹，加鹽會被判「多加了鹽」，太多會變成過鹹。

### 比對規則（已知／變體）

- 必要成分都要有（本來的食材或替代食材），至少一半是本來的食材。
- 多出來的食材依份量計權重：主要食材（肉、海鮮、豆腐、蛋）與主食算 2，其他算 1，辛香料不算；權重不能超過食譜的必要成分數。權重 ≤ 1 而且沒有替代、烹調方式也對＝已知食譜，否則＝變體（名稱「黑胡椒豬肉」「蒜香炒蝦（加蛋）」）。
- 多了主食（飯、麵、麵粉、吐司）而食譜裡沒有：已經是另一種料理，不算這道菜的變體（蒜香炒蝦＋義大利麵＝新創的蒜香蝦仁義大利麵）。
- 好幾道都符合時，取最接近的（本來的食材越多越好；多出來的食材比替代食材扣得多）。

### 今日特餐

每一班從 24 道裡挑兩道不同分類的特餐（獨立的亂數序列，同一個種子永遠同樣的特餐，不影響其他訂單），放在後半段（第 8、10 張；單人只有 7 張，第 6 張換成特餐）；前面維持招牌菜。廚房狀態的 `menu` 列出這一班會出現的食譜，開班說明與食譜手冊的「本班菜單」會顯示。


## 料理沙盒擴充 v3.0：第四階段（20 種主廚委託）

程式：`shared/src/kitchen/commissions.ts`（資料、條件說明、條件判定），`server/src/kitchen/scoring.ts` 的 `scoreCommission`（評分）。原本的「主廚自選」就是委託：訂單種類還是 `free`，`requestId` 指向委託（前五種委託就是原本的五種需求，換成結構化條件）。

### 資料結構

每份委託有：編號、名稱、主廚的原話、難度、必要條件（`require`）、加分條件（`bonus`）、風味目標（`taste`）、器皿與熱食、標準秒數、時限（限時委託）、特殊狀況（`effects`）、缺貨食材、可能的解法、獎勵。文字只給玩家看；伺服器只看結構化條件（`Cond`）：

| 條件 | 判定 |
| --- | --- |
| hot | 端上桌的溫度 ≥ 55°C |
| has／hasAll／forbid | 依食材 ID、分類或標籤：要有、都要有、不能有 |
| distinct | 蔬菜／主要食材（不算辛香料）／所有固體食材的種類數 |
| taste／tasteDiff／flavorVariety | 七維口味的區間、兩種味道的差距、吃得出幾種味道 |
| form／sauce／style | 成品形式、醬汁狀態、烹調方式（來自自由料理判定） |
| edible／notBurnt | 沒有致命失誤與食品安全問題／沒有燒焦 |
| noSeasoning／seasoningMin | 不能加某種調味料／至少加多少 |
| textures／crustSoft | 吃得出的口感（脆、外酥、軟嫩、彈牙、滑順）／外酥內軟 |
| onePot | 所有食材只待過一個熱源 |
| withinSec | 從出單到出餐的秒數 |
| quality | 料理品質（總分或某一項）的下限 |
| inBand／browned／melted | 指定食材熟度在「剛好熟」區間／表面上色／加熱融化 |
| kind／aromaticFirst | 新創或變體／先爆香 |

條件的說明文字（`condLabel`）和判定（`judge`）用同一份資料，所以訂單板上看到的條件就是伺服器檢查的條件。

### 評分（企劃書第七章）

- 品質 100 分：烹調 30、風味 25、搭配 20、質地與完成度 15、時間 10。前四項來自自由料理判定（風味依委託的風味目標）；時間：標準秒數內滿分，兩倍時間內遞減到 3 分，之後到 0。
- 加分條件：每做到一條加分，總分最多 100。食品安全的上限照樣適用。
- 必要條件和品質分開：違反任何一條＝委託沒有達成，分數最多 35，結果列出每一條違規原因；料理本身的品質還是照樣顯示（「很好吃的蛋料理，違反『不吃蛋』還是失敗」）。
- 等級：0–39 失敗、40–59 勉強完成、60–74 合格、75–89 優秀、90–100 主廚推薦（沒達成一律失敗）。
- 獎勵：基本遊戲幣 × 等級倍率（失敗 0、勉強 0.5、合格 1、優秀 1.3、主廚推薦 1.6）；用新創或變體料理完成再 × 1.2。
- 招牌菜的必要成分燒焦時，訂單分數最多 45（以前燒焦的蛋還能拿到 89 分）。

### 排程與特殊狀況

- 每一班的五張委託：前三張是入門委託（1–5 號洗牌，和原本的主廚自選一樣），後兩張是進階委託（6–20 號裡挑兩種，獨立的亂數序列）。
- 限時出餐：客人等的時間就是時限（150 秒），不因人數放寬。
- 異常廚房：這張單開著的時候溫度計失靈（只改變取得資訊的方式；熟度照樣看外觀、聲音、觸感或隊友回報），料理規則完全不變。
- 食材替代：牛肉「缺貨」只出現在條件與說明裡，用了就違規。

## 料理沙盒擴充 v3.0：第五、六階段（多人同步、平衡）

- 多人同步：所有料理狀態都只在伺服器（拌料、泡水、受熱紀錄、委託都在廚房狀態裡），操作依序處理、以 requestId 去重；同時搶食材、同時攪拌、同時出單都有測試（`sandbox-sync.test.ts`）。重連時伺服器送完整狀態，客戶端不保存任何料理資料。
- 恐怖事件：威脅系統拿不到任何料理資料（靜態掃描測試），而且「同樣的料理操作，有沒有怪物抓人，鍋裡、攪拌碗、烤箱的結果完全一樣」。異常廚房委託只讓溫度計失靈（資訊），不改任何料理規則。
- 平衡（`balance.test.ts`）的結論與因此做的調整：
  - 失敗料理的分數一定在 39 以下（等級一定是失敗）。
  - 不能生吃又沒熟的食材佔固體份量 40% 以上＝整道菜沒熟（以前生馬鈴薯一盤還能拿 60 分）。
  - 奶油這類煎炒用的油脂不判熟度（只看有沒有燒焦）。
  - 烤箱上色降到平底鍋的 0.18 倍（以前烤地瓜還沒熟就焦了）。
  - 食譜比對：多出來的主要食材權重 2、多了主食就不算這道菜；替代食材比多加食材更接近原本的食譜。
